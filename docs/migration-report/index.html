OneNote Account Migration and Project Context

A private reconstruction of why the notebook moved, what the project was meant to accomplish, and what the surviving transcript can actually prove. Updated November 21, 2026.

Bottom line: moving the notebook from the University of Toronto Microsoft 365 account to Samira’s personal Microsoft account was not inherently required by the Microsoft Graph OneNote API. Graph supports notebooks in both personal and organizational accounts. The migration was nevertheless a practical way to remove institutional consent and account-lifecycle constraints, and it was required by this project’s current personal-account-only authentication configuration unless that configuration was changed.

What the Original Project Was For

The notebook was functioning as a structured research-paper library: OneNote sections organized topics, OneNote pages held individual papers or related notes, and the papers themselves were embedded PDFs. The core problem was not simply synchronization. It was that browsing and searching many embedded papers through OneNote was too slow and fragmented.

The intended custom system was meant to preserve OneNote’s organization while adding capabilities that OneNote did not provide cleanly:

  • search PDF contents across the entire library;
  • identify the OneNote section and page containing each result;
  • identify the exact PDF page containing the match;
  • open the original PDF at the match with visible highlights and selectable text;
  • eventually answer natural-language questions from retrieved passages with source citations.

What Was Actually Implemented

Implemented

Notebook/section/page browsing, local PDF caching, page-level text extraction, global search, grouped results, PDF-page navigation, and selectable PDF.js highlights.

Still Planned

OCR for image-only printouts, stronger ranking and query syntax, and an embedded AI assistant that answers from controlled retrieval context with citations.

Was the Personal-Account Migration Necessary?

Not as a Microsoft Graph requirement

Microsoft states that the OneNote Graph API can access notebooks in a personal or organization account, including consumer OneDrive and OneDrive for Business. The delegated Notes.Read permission is the correct read-only scope for the signed-in user’s notebooks. In principle, the application could therefore have remained connected to the U of T notebook.

But the current application is configured for personal accounts only

The repository’s example configuration uses https://login.microsoftonline.com/consumers. Microsoft defines that authority as accepting personal Microsoft accounts only. A U of T work/school identity cannot authenticate through it. Keeping the institutional account would have required an app registration whose supported account types included organizational accounts and an authority such as the U of T tenant, organizations, or common.

Institutional policy could still have blocked the alternative

Organizational tenants can restrict whether users may consent to applications. Even permissions that do not normally require administrator consent can be subject to tenant consent policies, risk controls, app-assignment requirements, or an admin-consent workflow. The surviving transcript says the U of T access was restricted, but it does not preserve the exact error or policy response. It therefore cannot prove that migration was the only possible solution; it can only show that migration was the solution that successfully removed the dependency.

What the migration bought in practice

  • control over the Entra app registration and consent path;
  • notebook ownership independent of university account policy;
  • continuity if institutional access, licensing, or enrollment later changes;
  • a predictable personal-account authentication target for this local tool.

Those benefits explain why the migration was reasonable even though the API itself did not mandate it. The cost was the difficult, lengthy notebook transfer and synchronization process.

Best Interpretation Going Forward

The product should be understood primarily as a local research-library interface layered over OneNote, not as a synchronization utility. Synchronization and account migration were enabling work. The user-facing objective is faster cross-paper discovery without giving up OneNote’s subject organization or the original PDFs.

A sensible next phase would build on the existing search index rather than revisit the migration:

  1. improve coverage reporting so “not found” can be distinguished from “not indexed”;
  2. add OCR for printout-only pages;
  3. improve relevance ranking, phrase search, and field filters;
  4. add citation-first AI question answering over retrieved PDF-page passages.
